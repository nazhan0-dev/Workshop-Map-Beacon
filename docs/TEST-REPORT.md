## 1. ปัญหาที่พบและการแก้ไข

ระดับ: **สูง** = ข้อมูลรั่ว/ถูกยึดบัญชี/ข้อมูลผิด · **กลาง** = ใช้งานผิดพลาดหรือเสี่ยงเมื่อขึ้นจริง · **ต่ำ** = ความเรียบร้อย

### ความปลอดภัย

| # | ระดับ | ก่อนแก้ (ทดสอบซ้ำได้) | แก้อย่างไร | เทสต์ที่คุม |
|---|---|---|---|---|
| S1 | สูง | token เก็บใน `localStorage` ถ้ามีช่อง XSS สคริปต์จะขโมย token ไปใช้ได้ 7 วัน | ย้ายไป cookie `httpOnly` + `SameSite=Lax` + `Path=/api` (+`Secure` ตอนใช้งานจริง) และไม่ส่ง token ใน body | API: security / หน้าเว็บ: cookie อ่านจาก JS ไม่ได้, ไม่มี token ใน localStorage |
| S2 | สูง | ลบบัญชีแล้ว token เดิม**ยังเรียก API ได้** (`GET /me/assignments` → 200) | middleware โหลดผู้ใช้จากฐานข้อมูลทุกคำขอ ไม่พบ → 401 และสั่งลบ cookie | API: security (ลบบัญชี) |
| S3 | สูง | admin รีเซ็ตรหัส หรือผู้ใช้เปลี่ยนรหัสแล้ว token เก่า**ยังใช้ได้** | เพิ่ม `users.token_version` ใส่ไว้ใน token และเพิ่มค่าเมื่อเปลี่ยน/รีเซ็ตรหัสหรือกดออกจากทุกอุปกรณ์ ส่วนเครื่องที่เปลี่ยนรหัสได้ cookie ใหม่ | API: auth, security / หน้าเว็บ: ถูกรีเซ็ตรหัสแล้วเด้งออก |
| S4 | กลาง | ลดสิทธิ์ admin แล้วยังเป็น admin ต่อจนกว่า token หมดอายุ | อ่าน role จากฐานข้อมูลทุกคำขอ มีผลทันที | API: security (ลดสิทธิ์) |
| S5 | สูง | ไม่จำกัดการเดารหัส (ผิด 10 ครั้งติดได้ 401 ทุกครั้ง) | จำกัด 5 ครั้ง/ชื่อผู้ใช้/IP ใน 15 นาที และ 30 ครั้ง/IP ตอบ `429` พร้อม `Retry-After` | API: เดารหัสผ่าน |
| S6 | กลาง | เดาได้ว่าชื่อผู้ใช้ไหนมีจริงจากเวลาตอบ (มีจริง 85 ms / ไม่มี 8 ms) | เทียบ bcrypt กับ hash หลอกเมื่อไม่พบผู้ใช้ เวลาตอบใกล้เคียงกัน | ตรวจด้วยมือ |
| S7 | กลาง | ไม่มีการกันยิงคำขอข้ามเว็บ (CSRF) เมื่อเปลี่ยนมาใช้ cookie | ตรวจ Origin/Referer ของคำขอแก้ข้อมูลที่ใช้ cookie และการล็อกอิน, CORS อนุญาตเฉพาะ `CLIENT_URL` (ใส่ได้หลายที่) | API: CSRF จาก Origin/Referer, CORS preflight |
| S8 | ต่ำ | เปิดเผย `X-Powered-By: Express` และไม่มี security header | ปิด header นี้ เพิ่ม `nosniff`, `X-Frame-Options: DENY`, CSP, `Referrer-Policy`, `Cache-Control: no-store` | API: header |
| S9 | กลาง | ใช้ `JWT_SECRET` ค่าตัวอย่างตอนใช้งานจริงได้ | production ไม่ยอมเปิดถ้า secret สั้นกว่า 32 ตัวหรือยังเป็นค่าตัวอย่าง และกำหนดอัลกอริทึม `HS256` ตายตัว | ตรวจด้วยมือ / API: token `alg: none` ถูกปฏิเสธ |

### ความถูกต้องของข้อมูล

| D4 | กลาง | จัดเวรให้บัญชี admin ได้ | รับเฉพาะผู้ใช้ role USER | API: security |

## 5. สิ่งที่ตรวจแล้วไม่พบปัญหา

- SQL ทุกคำสั่งใช้ placeholder ไม่มีการต่อข้อความจากผู้ใช้ลงใน SQL
- ข้อความบนหมุดแผนที่ (สร้างเป็น HTML) escape ชื่อจุดและชื่อคนแล้ว ส่วนอื่นใช้ React ซึ่ง escape เอง ไม่มี `dangerouslySetInnerHTML`
- ไม่มี `console.log` ค้างในหน้าเว็บ
- รูปแนบตรวจชนิด (jpeg/png/webp) และขนาดที่ server
- สิทธิ์ดูรายงาน: รปภ. เห็นเฉพาะของตัวเอง หัวหน้า/รองเห็นเฉพาะกะที่ตัวเองเข้าเวร

## 6. ข้อเสนอแนะก่อนขยายระบบ

1. **ขึ้นเว็บแบบ HTTPS** จำเป็นทั้งกับ cookie แบบ Secure และ GPS บนมือถือ
2. ใช้ server หลายตัวเมื่อไหร่ ให้ย้ายตัวนับการเดารหัสไป Redis
3. ย้ายรูปแนบจากฐานข้อมูลไปที่เก็บไฟล์ (S3 / Cloudflare R2) เมื่อข้อมูลเยอะ
4. แจ้งเตือนแบบ push (Web Push / LINE Notify) สำหรับรายงานด่วนและคนยังไม่มาเข้ากะ
5. เพิ่ม CI (GitHub Actions) ให้รัน `npm run test:unit`, `npm run lint`, `npm run build` ทุก push
6. บันทึกประวัติการแก้ไข (audit log) ว่าใครจัด/ย้าย/ถอนเวรเมื่อไหร่
